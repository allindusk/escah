2. **过时计划归档**：把已被取代的两份计划文档归档，保持工程整洁。

## 产品概述

在不引入新架构的前提下，复用现有「词表替换引擎 + LLM API 管线」链路，对当前真实残留（排除已译 key 后）再做一次多模型并发翻译与幂等注入，随后重跑应用链重建 dist；同时把已被 API 管线方式取代的两份计划文档移入 archive 子目录，避免误导后续维护。

## 核心功能

- 多模型并发翻译：glm-5.1/glm-5.2 + deepseek-v4-pro，额度耗尽由既有 model_dead/health 逻辑自动切换。
- 重新导出当前真实残留 → 拆分 → 翻译 → 注入（保留 `is_japanese_variant` 专名幻觉变体过滤、幂等跳过已存在 key）。
- 应用链重建 dist：zh_patch → char_zh → sync-site → node build.mjs build。
- 归档 `esca-translation-finish` 与 `修复图片路径并由助手直接翻译` 两份计划到 `.codebuddy/plans/archive/`。
- 验证全站残留字符数与角色 JSON 残留单元格数较上轮下降。

## 技术栈

- 复用现有 Python 翻译管线：`tools/_api_pipeline.py`（OpenAI 兼容客户端，`base_url=tokenhub.tencentmaas.com/v1`）、`tools/_export_for_api.py`、`tools/_split_for_api.py`、`tools/_inject_batch.py`。
- 词表引擎：`tools/zh_patch.py`（JA2ZH 现 26,928 条）、`tools/char_zh.py`（角色 JSON 补 zh）。

- 无新增依赖、无新增密钥；deepseek-v4-pro 复用现有 API_KEY 与端点。

## 实现方案

- **策略**：先清掉上一轮（已注入）遗留的 001/002 批次中间产物，避免重翻已译内容浪费额度；再重新导出"排除已译 key 后的当前真实残留"，拆分后由多模型管线翻译、过滤、注入；最后重跑应用链重建 dist。计划文档直接移动归档（非删除，符合回收站约定）。
- **关键技术决策**：

1. `MODELS` 增加 `deepseek-v4-pro`，依赖管线既有的轮询 + `model_dead` 自动切换：GLM 额度耗尽即停用，deepseek 自动接管，零人工介入。
2. `token_budget` 由「统一 50 万」改为**按模型分别预算**（glm 各 50 万、deepseek ~20 万），防止单一模型超额。
3. `extra_body={"thinking":{"type":"disabled"}}` 是 GLM 专属参数，对 deepseek 可能报错 → 改为仅 `"glm" in model` 时附加，避免 deepseek 调用失败。
4. 旧批次与结果**移入 `recycle_bin/tools/`**（不 `git rm`、不永久删除），遵循"不永久删除"最高优先级约定。

- **性能与可靠性**：沿用既有每模型限速器（RPM 60→间隔 1.1s）、429 退避、partial checkpoint、断点续跑；注入端按 `[N]` 序号配对（非行序）杜绝错位污染。应用链全程 detached + `PYTHONIOENCODING=utf-8` 防止 Win GBK 崩溃与 harness 强杀。
- **避免技术债**：仅在 `_api_pipeline.py` 做最小改动，不改拆分/注入配对逻辑（历史错位事故教训）；`_split_for_api.py` 的 batch 内 `[N]` 全局唯一不可回退。

## 实现注意事项

- 翻译前**必须**先移动旧 001/002 批次与结果，否则 `main()` 会复用已译结果、跳过真正待译段。
- deepseek-v4-pro 是否真在该端点可用以实测为准；若不可用，`mark_dead` 自动停用、GLM 继续，不影响整体链路。
- 诚实预期：本轮新增可注入对数量有限（可能几十~一两百，因剩余多为专名），角色 JSON 残留会随词表增长再降；如要接近零残留需后续从 `_rejected.json`+`_freq_chars.py` 手工挑真散文补译（超出本次范围）。
- 归档为移动文件（新建 `.codebuddy/plans/archive/`），不删除；`.codebuddy/` 已被 git 跟踪，归档后由后续 commit 一并提交（本次不 commit）。

## 架构设计

完全复用现有"流水线数据层 → 词表引擎 → VitePress 站点层"分层（以文件为契约）。本次不新增模块、不改组件，仅在翻译 runner 做最小配置增强，并在 plans 目录内做目录级归档。链路：`_export_for_api.py` → `_split_for_api.py` → `_api_pipeline.py translate/inject` → `_inject_batch.py(写 JA2ZH)` → `zh_patch.py`+`char_zh.py` → `sync-site` → `build.mjs build` → `dist`。
