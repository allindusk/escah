# 2026-08-05 工作日志

## 角色名浮窗失效——根因是 `_apply_glossary_to_i18n.py` 没跑

### 用户核心反馈
"很多页面的角色名因为翻译错了，无法激活浮窗" + "原本项目里就有把 name 词汇表注入所有页面 i18n 的脚本，你分析为什么那个脚本没生效（不用重写很多代码）"。

### 根因（脚本为什么没生效）
1. `_apply_glossary_to_i18n.py` 本身逻辑没问题：规则0（整条 ja==词表键→直接设标准 zh）、规则1（分段对齐逐段替换）。但它**不在标准 CI/构建流程里**——是手动工具。
2. 翻译流程 `i18n build→extract→译→fill→char-fill→sync-site→build` 里，**fill（填 LLM 译文）在烘焙之后又把角色名 zh 写成了音译/异译（如「青龙天 库奇纳瓦」「昂战小队」）**，覆盖了之前烘焙的标准译名。
3. 之后没人把烘焙脚本作为"翻译回填后必跑步骤"重跑 → 正文中文名与 `charRefs.nameAliases`（由 names.yaml 生成）不匹配 → 前端 `wrapPlainTextNames` 按 nameAliases 中文名做纯文本匹配打 `data-char` 失败 → 浮窗全站失效。
4. 脚本固有盲区：ja 是整句（含角色名作子串）、zh 是音译整段时，规则0（整条不匹配）和规则1（段数不等跳过）都救不了——这类整块散文段落残留（如 awakening 的"青龙天 库奇娜娃"）。

### 已执行修复
- 重跑 `python tools/_apply_glossary_to_i18n.py`：实际写入 **572 文件 / 9294 条目**统一成 names.yaml 标准译名（之前从没在最新译文上跑过，所以"没生效"）。
- `sync-site` 重生 charRefs.json（737 别名），nameAliases 已含全部标准译名（超昂闪忍成香/艾斯卡蕾雅/青龙天久名和 等均已验证在 aliases 里）→ 前端能匹配 → 浮窗恢复。
- 验证：wide-battle / b-universe / annihilation / raid 等页角色名渲染均为标准译名（如「青龙天久名和」），b-universe 那处节点级 data-char 正常。

### 结论与铁律
- ⚠️ **`_apply_glossary_to_i18n.py` 必须作为"翻译回填（fill）之后、sync-site 之前的必跑步骤"**（手动或写进脚本链）。否则每次翻译更新都会让角色名退化为译文填的译法、浮窗失效。这是"翻译被改导致浮窗丢"的根本预防手段。
- 残留极少数整块散文音译段落（脚本盲区）需靠翻译质量或后续单独处理，不影响主流程恢复。

## 角色名浮窗失效修复（b-universe 单页，上午先做的）


### 现象
用户报 `zh/b-universe.html#content_1_24` 角色名「青竜天クチナワ」在 zh 页渲染成「青龙天 库奇纳瓦」且浮窗失效（无 `data-char`）。names.yaml 权威译名是「青龙天久名和」。

### 根因（两层）
1. **翻译数据坏**：`data/parsed/i18n/b-universe.json` 的 `blk176.zh` 是早期 LLM 音译「青龙天 库奇纳瓦」（与 names.yaml 权威译名「青龙天久名和」不一致）。
2. **渲染退化触发**：blk176 的块内 `key914.zh`、`key915.zh` 漏译为空字符串 → 渲染层 `i18n.py:1738` 的 `all(key.zh for k in blk.keys)` 为 False → 不 continue（不走节点级）→ 整块退化到块级回退，用音译 `blk176.zh` 整段输出。
3. 音译「青龙天 库奇纳瓦」与前端 `charRefs.json`/nameAliases 的「青龙天久名和」不匹配 → `wrapPlainTextNames` 纯文本打 `data-char` 失败 → 浮窗丢失。
   - 注：ja 页同类角色名是日文原文，能在 nameAliases 命中 → 浮窗正常，所以用户只觉 zh 页丢。

### 修复（定点改 i18n 真值，非渲染层）
- 补全 `key914.zh` = " 30秒+全体1倍+诅咒50% 敌方目标（全体2倍+每秒"、`key915.zh` = " 伤害+确定诅咒）"（与 blk176.zh 对应段一致）。补全后 `all(key.zh)` 为真 → 走节点级，`key913` 经 `_name_override("青竜天クチナワ")` 出「青龙天久名和」→ 前端匹配 nameAliases「青龙天久名和」→ 浮窗恢复。
- 同步把 `blk176.zh` 音译改为「青龙天久名和 30秒+...」（干净真值，即使不用也修正）。

### 验证
- `render_locale("b-universe","zh")` 输出 `<span style="color:blue;">青龙天久名和</span> 30秒+...` ✓
- 全站扫描「含 keys 且任一 key.zh 为空」的块 = 0（b-universe blk176 是最后一个漏译块，修完即全站清零）。
- wide-battle / characters / annihilation 该角色渲染均 `data-char="青竜天クチナワ"` 正常（annihilation 按设计保留日文名+头像，符合"角色名保留日文"约定，非 bug）。
- 已 `sync-site`（重生成 1326 页 md + charRefs.json）。

### 结论
"很多页面浮窗失效"实际仅 b-universe blk176 一处（音译+key 漏译退化）。其余页角色名走节点级 `_name_override` 已纠正为标准译名，浮窗正常。用户感知可能来自旧 dev 缓存；5173 dev 需 sync-site 后刷新。

### 重要机制备忘（浮窗）
- 浮窗 trigger 依赖 `data-char`（=日文角色名 key）。来源三处：① `tagCharLinks` 给 `characters/名.html` 的 `<a>` 打；② `tagAvatars` 给头像 `alt/title` 打；③ `wrapPlainTextNames` 在正文纯文本里按 `nameAliases`（中文名→日文名）正则匹配中文名包 `<span data-char>`。
- **关键**：zh 页正文里的角色中文名必须 === `charRefs.nameAliases` 的 key（= names.yaml 译名），否则纯文本匹配失败、浮窗丢。所以"翻译被改成非标准中文（音译/异译）"会直接废掉浮窗。
- 渲染层 `_name_override` 对节点级 key 命中 names.yaml 时会强制覆盖成标准译名（救回浮窗）；但**块级退化用 `blk.zh` 时 `_name_override` 只对整句查（查不到）**，只能靠 `_correct_text` 子串替换——音译形态与 names 译名差异大时救不回。故音译/错译必须烘焙进 i18n JSON 源头（与既有铁律一致）。

## ⚠️ 全站最终结论（修正早间判断，2026-08-05 晚）

### 早间判断被推翻的点（如实记录，避免后人误信）
1. **"今天会话开头的 9294 条烘焙破坏全站浮窗" 是错的**。9294 条烘焙只是把音译/异译统一成 names.yaml 标准译名（与 charRefs 一致），反而**有利于**浮窗匹配。中途 git checkout 还原 i18n → 加空保护重跑（4924 条）→ 加规则2' 修正专名幻觉，是稳妥收口，但"破坏"定性不成立。
2. **"b-universe 那批角色名大多无角色卡页、浮窗会404" 是错的**。用 `_map_buniv_names.py` 实测：b-universe 出现的 100 个 names.yaml 角色名，绝大多数 `ja` 本就是 characters/ 角色卡 page key、且中文名命中某角色卡 name_zh。仅少数（如 タイガージョー/猛虎乔）无卡页，属少数。
3. **"grep dist 静态 HTML 看不到 data-char = 浮窗消失" 是错的（最严重的方法论错误）**。`data-char` 由 `MirrorContent.vue` 的 `onMounted→processEl→wrapPlainTextNames` **客户端运行时注入**，`dist/*.html` 静态文件里**根本没有** data-char，必须浏览器渲染后才有。我用静态 grep 验证浮窗，必然得 0，导致一路误判"浮窗失效/没数据"。

### 确凿结论（多重验证）
- **中文名浮窗已全站正常工作**：`charRefs.nameAliases` 含中文名→日文key 映射（如 `翼龙剑圣茜→翼竜剣聖アカネ`），前端 `wrapPlainTextNames` 正则能匹配。用 python 模拟同款逻辑对 dist b-universe.html 跑，模拟注入 **808 个 data-char 浮窗**，含全部纠结的中文名（翼龙剑圣茜/神骑维阿尔/青龙天久名和/魔女绮蕾/神骑布罗库米艾尔/七贤腕夏姆艾尔/幻忍菊理 等）。→ 用户需求"中文名也要浮窗"**天然已满足**，无需改前端。
- **超链接（faq/raid `<a>` 壳）未被破坏**：超链接是服务端渲染（render_locale 产出），静态可见。全站校验（`_verify_bake_nolink_conflict.py` 遍历 158 个含 `<a>` 模板页、对比烘焙前后链接锚定命中）= **0 冲突**，且 1 个改进（幻觉名改回权威译名后更易命中）。
- **烘焙脚本 `_apply_glossary_to_i18n.py`（规则0/1/规则2'）与超链接代码无冲突**：两件事消费 blk.zh 同源词表（names/skills/terms/link_terms），只把 LLM 错译/幻觉改成权威译名。
